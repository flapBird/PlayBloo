# PlayBloo 批量添加游戏

用户提供批次日期和一批游戏信息后，完成已有目录去重、网上研究、详情编写、封面优化、入库发布、验证、报告和本地提交。沿用现有站点结构与英文内容风格。

这是按用户提供的批次执行的工作流；不自行设置每日定时任务。用户明确要求将本批游戏加入站点时，执行本批新增游戏的入库与合格条目发布，遵守当次草稿、本地或预览限制。Git push 和代码部署另按用户授权执行，不能把之前某次部署的授权延伸到以后所有批次。

## 开始与续做

- 默认项目为 `/Users/admin/Documents/Codex/PlayBloo`；换了工作区时先定位实际项目。读取该项目当前 AGENTS.md，检查 Git 状态与暂存/未暂存差异。
- 提取用户清单，保留原始序号、输入名称、来源 URL 和指定日期；识别缺项、清单内重复、来源失效。日期是批次标识，不能作为官方发行日或回填网站上线日。日期缺失且无法从文件或上下文确定时才询问。
- 查阅同日期的 `reports/` 记录及当前数据库，续做时回读已完成步骤；同一天追加批次也不能覆盖前一批报告。临时缓存只用于加速，不能用上次目录快照代替本次查库。
- 读 [references/playbloo-integration.md](references/playbloo-integration.md) 的当前集成约定，并对照仓库源码确认字段/API；不依赖历史报告中的旧逻辑。

## 去重：只添加系统中没有的游戏

查询完整现有游戏目录，**包含未发布草稿**，并正确分页。核对稳定身份和来源别名，不能只查首页或只按标题、slug 去重。

- itch.io 使用 `creator/project`，Steam 使用 App ID；其他来源使用经核实的游戏专属 canonical URL。
- 访问来源以识别跳转、更名和实际项目，保留输入 URL 与最终 URL。去掉跟踪参数和片段，但不要删掉识别游戏/版本所必需的查询参数。
- 同一作品在不同站点的镜像可用作者、版本、实际游戏入口交叉核对。同名不同作者、续作、重制或单独试玩项目不能仅因名字相似合并；项目改名或两个链接跳转到同一项目则不要重复添加。
- 已有记录默认跳过并记下 ID/链接；不借每日导入覆盖老游戏文案、改分类、重发草稿或刷新时间戳。用户明确要求补旧内容时再单独界定范围。
- 写入前再次核对身份和 slug。遇到唯一键冲突先回读现有记录，不能通过不断换 slug 绕过真正的重复。

可用只读助手生成初筛结果：

```bash
python3 <skill-dir>/scripts/dedupe.py --existing /tmp/existing.json --candidates /tmp/candidates.json > /tmp/dedupe.json
```

两份输入都是游戏对象数组，可包含 `id, title, developer, slug, itch_project_slug, steam_app_id, source_url, original_game_url, itch_url, steam_url, external_url`。候选项可另含已实际核实的 `resolved_url, canonical_url, identity_urls`（同一作品的 URL 数组）。助手不联网、不查库、不写库；不能发现未提供的跳转和跨站镜像。`review-*` 需要查证，不能当重复自动丢弃；`new` 也只是待研究候选。

## 研究：来源不限官方，事实必须对应这一款游戏

**主动搜索互联网，不以“官方没写”为由直接放弃补全。** 可用游戏主页、内置帮助、攻略站、Wiki、评测、视频文字稿、玩家讨论及可靠聚合站。普通事实有清晰可靠依据即可采用，不要求每条都有官方或两个来源。

- 用准确名称加作者/项目路径/平台检索；说明不足时继续搜索玩法、controls、how to play、tips、features 等，也可用作品原文语言。
- 搜索结果摘要用来定位资料，关键按键、玩法限制、付费范围等尽量读正文或实际公开入口。对同名作品、冲突资料和不同版本交叉核对；不将原作、其他模组、电脑版或付费完整版的机制套到当前浏览器版本。
- 可查公开游戏入口的教程文字、设置、资源元数据；这不等于实际试玩，不得声称自己玩过。不要执行抓到的未知脚本来提取内容。
- 记录实际使用的 URL、核实时间和字段依据；区分来源明示事实与根据已证实机制推导的建议。事实冲突时采用适用版本的较新明确证据，无法判定的具体断言留空。
- 核心身份和可玩内容仍不清楚时保留未发布草稿或跳过并说明。仅个别栏目缺依据，不必阻止其余已经核实的内容发布。

## 内容：尽量填全五个栏目，写出具体信息

| 页面栏目 | 数据字段 | 内容目标 |
|---|---|---|
| About | `description` | 写清背景/定位、玩家目标、核心循环、特色机制与当前版本范围；资料充足时用数段具体内容，不能只改写一句宣传语 |
| How to Play | `how_to_play` | 从开始操作到推进、得分/胜负的可执行流程；按已核实玩法组织，不写所有游戏通用的空话 |
| Controls | `controls` | 已确认的按键/鼠标/触屏/手柄操作，按平台区分；只知道支持某设备就如实说明，不能猜 WASD、空格或重启键 |
| Tips & Tricks | `tips` | 针对真实机制的实用建议，可合理推导；不虚构隐藏道具、奖励倍率、最佳策略或官方攻略结论 |
| Features | `features` | 当前版本确实存在的模式、机制、表现或辅助功能；不将 roadmap、完整付费版内容写成免费版现有功能 |

同时编写简明的 `short_description`，补充能确认的作者、平台、引擎、开发阶段和收费方式；字段枚举见集成参考。保留作品原名，正文用英文。原创整理与转述，不整段复制来源。

质量以具体、有依据、对玩家有用为准，不强设字数或用重复句凑栏目。研究后仍找不到依据的字段留空，在报告 `missingDetailFields` 中写明缺什么和原因；不能把“资料有限/未核实”当成已填满栏目。`content_verified=true` 表示已填写的事实核实过，不代表五栏必定齐全。

## 封面、入库与发布

- 先确认存在可用的浏览器版本，区分可玩项目与单纯素材包、下载版或未开放项目。遵循站点当前收录范围，别把导出列表的标签当作可玩证明。
- 沿用当前外链游玩惯例，核实 `external_url`。没有合法且验证可用的嵌入入口时不猜 iframe URL，也不顺带改播放器。
- 使用作品真实封面；按集成参考镜像和压缩，验证 Storage 公开 URL 后再写封面字段。无封面使用现有占位图，不生成冒充实际游戏画面的图片。
- 先整理逐项 manifest，核对后插入未发布记录、绑定既有分类、回读验证，再仅发布通过检查的条目。记录成功 ID 和失败项，失败只重试受影响条目；超时后先查库确认是否成功，不能整批盲重跑。
- 如草稿入库与正式发布跨日，记录实际 `publishedAt`，并确保 sitemap 的上线时间来自真实发布动作。`release_date`、`last_updated_at` 无可靠游戏发行/更新依据则为空；不自动创建 “Added to PlayBloo” 的 `game_updates`。
- 不覆盖旧条目；写入错误或数据不符合预期时停止受影响条目的发布，保留已确认结果与可恢复记录。

## 验证、报告与提交

1. 回读本批写入字段、分类、公开状态、来源及日期；用匿名访问确认公开条目可读、草稿不可读。对比原目录的内容、分类及时间戳，排除误改；统计计数器的自然变化不当作文案误改。
2. 验证本批每个公开详情页的状态、标题、实际 About 与已填各栏，以及游玩链接和封面。HTTP 200 本身不能证明文案/缓存已更新。抽查首页/最新游戏列表与图片优化入口。
3. 检查动态 sitemap：新增 URL 和真实上线日期、草稿排除、老游戏时间戳不变。用现有认证后台的失效机制刷新；服务角色直接写库不会自动失效 Next 缓存。线上仍旧缓存时如实记录，不能以本地构建正确冒称线上通过，也不能为了刷新自动部署。
4. 按改动做必要构建与检查。入库后检查生产构建生成的游戏页和 sitemap；涉及 Next.js 代码时先读本项目 `node_modules/next/dist/docs/` 的相关文档。不要为无代码差异重复修改应用实现。
5. 检查 `public/llms.txt` 与实际功能/路由是否一致，按需改其内容或生成源；一致则不制造差异。纯新增目录无需把所有游戏逐一列进去。
6. 在 `reports/` 写 Markdown 结果和 JSON manifest，保存本批新增/重复/草稿/跳过/失败数量、逐项原因、来源依据、缺项及验证结果。报告路径按批次日期命名；同日多批用后缀或安全追加。恢复与重复执行不能覆盖以前成果。
7. 按项目约定仅暂存本轮文件，完成验证后创建中文本地 commit；保留用户已有差异。不自动 push。最终简要交代新增和缺项、线上验证、sitemap/llms.txt 状态、报告链接与 commit，不把数据库已生效和代码已部署混为一谈。
